# 文档解析方案调研

> 关联特性：private-chat-attachment-parsing（私聊附件解析）
> 目的：调研业界主流文档解析方案，对比 brain 现状与已提方案的差距，为设计阶段决策提供依据。
> 说明：本文档为调研与建议，不锁定最终方案；耗时类数据需以实测为准。
> 部分外部来源内容为合规改写。

---

## 一、当前主流文档解析方案（2025–2026）

按"自托管纯库 → 自托管面向 LLM → 托管 API → 多模态/VLM"四档排列。

### 第 1 档：纯文本抽取库（自托管，免费）

| 工具 | 特点 | 短板 |
|------|------|------|
| **PyMuPDF** | 业界公认最快的纯 Python PDF 抽取库，benchmark 称 500 页 PDF 数秒内、速度为 pypdf/pdfplumber 数倍 | 整文档一次性处理时需注意内存管理 |
| **pypdf**（brain 现用） | 纯 Python、易用 | 速度与复杂版面处理弱于 PyMuPDF |
| **pdfplumber** | 表格抽取、版面保留最准，内存占用低 | 速度慢 |

> 学术对比 [arXiv 2410.09871](https://arxiv.org/html/2410.09871v1)：文本抽取上 PyMuPDF、pypdfium 普遍优于其他；但所有解析器在科技/专利类复杂文档上都吃力。

### 第 2 档：面向 LLM、直接输出 Markdown（自托管，免费）← 最契合本项目

| 工具 | 特点 |
|------|------|
| **PyMuPDF4LLM** | PyMuPDF 扩展，直接把 PDF 转 GitHub 风格 Markdown（识别标题、粗体、列表、表格、代码块），专为 LLM/RAG 设计 |
| **Docling**（IBM，MIT 开源） | PDF/DOCX/PPTX/HTML/图片 → Markdown，支持 OCR、表格抽取、CPU/GPU、批处理、同步/异步 |
| **MinerU**（开源） | 复杂 PDF/Office → LLM-ready markdown/JSON，面向 agentic 工作流 |

来源：[PyMuPDF4LLM 文档](https://pymupdf4llm.readthedocs.io/)、[docling-api](https://github.com/drmingler/docling-api)、[MinerU](https://github.com/opendatalab/MinerU)。

### 第 3 档：托管解析 API（按页付费，最准）

| 工具 | 特点 |
|------|------|
| **LlamaParse** | 复杂 PDF 准确率高（约 92% F1），多模态 LLM 驱动，约 $0.10/页 |
| **Unstructured.io** | 支持 30+ 文件类型，内置分块 + LangChain 集成，LLM 应用常用默认 |
| **Reducto / AWS Textract / Google Document AI / Azure Document Intelligence / Mistral OCR** | 企业级，强 OCR/版面分析 |

来源：[vstorm 2026 榜单](https://vstorm.co/llamaindex/top-10-document-parsing-services-for-rag-pipelines-and-llm-applications/)、[firecrawl](https://www.firecrawl.dev/blog/best-document-parsing-apis)。

## 二、brain 现状 vs 主流方案的差距

brain 现状（基于代码确认）：PDF=pypdf、DOCX=python-docx、XLSX=openpyxl、PPTX=python-pptx，输出**纯文本字符串**，不输出 markdown、不做 OCR、不落地文件。

| 维度 | brain 现状 | 主流做法 | 差距 |
|------|-----------|---------|------|
| 输出格式 | 纯文本，丢失结构 | Markdown（保留标题/表格/列表） | ⚠️ 大模型读 markdown 理解力明显更好 |
| PDF 速度 | pypdf（偏慢） | PyMuPDF（快数倍） | ⚠️ 观察到的"慢"很可能源于 pypdf |
| 扫描件/图片 PDF | 抽不出文字 | Docling/VLM 有 OCR | ⚠️ 扫描版 PDF 直接失败 |
| 表格 | docx 表格勉强、PDF 表格差 | pdfplumber/Docling 强 | ⚠️ |
| .doc 老格式 | 用 docx 库硬试，会失败 | 需专门处理 | ⚠️ |

**结论**：brain 能用，但属于最基础那一档——又慢又丢结构，且不支持扫描件。

## 三、解析能力交付给 agent 的方式（架构对比）

业界两条路线，可组合使用：

- **预处理管线（后端先解析好）**：摄取预处理 → 解析 →（复杂场景上 VLM），见 [Reducto build-vs-buy](https://reducto.ai/blog/build-vs-buy-ai-document-ingestion)。
- **按需工具（agent 自己调）**：
  - **MCP server**：运行时性能、鉴权更强（如 [Foxit 暴露 30+ PDF MCP 工具](https://developer-api.foxit.com/developer-blogs/use-cases-workflow-examples/automated-document-pipelines/foxit-mcp-server-ai-pdf-tools/)）。
  - **Skill / 渐进式披露**（Anthropic Claude Agent Skills）：按需加载，**省上下文、提升工具调用准确率**；[mcpjam 分析](https://www.mcpjam.com/blog/claude-agent-skills) 指出 MCP 在运行时性能与授权上仍有优势。

### 对本项目（openclaw 生态）的具体结论

- 已有 skill 机制（插件同步 SKILL.md），"解析 skill"是顺路的。
- **关键前提**：本地虾跑在用户机器上，**连不到内网 brain**（默认 `localhost:8000`）。走 skill 必须先由 opincer-service 暴露一个**公网、带 API Key 鉴权**的解析接口。
- **可靠性风险**：skill 依赖模型"主动想到去调"，弱模型可能不调 → 仍可能"看不到"。后端注入式不依赖模型聪明程度。

## 三种落地方式对比

| 方案 | 谁触发解析 | 优点 | 缺点/前提 |
|------|-----------|------|----------|
| 后端投递前解析 | opincer-service | 虾无需感知；本地/云虾天然一致；不暴露文件给本地环境 | 慢解析需异步；改后端管线 |
| 插件 channel.ts 解析 | 插件 | 不改后端 | 本地虾需能连 brain |
| **Skill / 工具按需调** | 虾自己按需调 | 懒加载、最省上下文、可自行分块、本地云虾同一份 skill | 需后端暴露公网鉴权接口；依赖模型主动调用；需限流防滥用 |

## 四、之前所提方案的缺陷（自查）

1. **耗时数字（"几十页一两秒"）是无依据臆测**，已撤回，应以实测为准；根因很可能就是 brain 用了 pypdf 这种慢库。
2. **"截断纯文本注入"丢结构**：markdown 结构被拍平，表格/标题丢失，模型理解力下降。主流是给 markdown。
3. **未考虑扫描件/图片型 PDF**：brain 和原方案对扫描件均会失败，而真实用户文件中很常见。
4. **思路局限在"塞 vs 不塞"**，未把 skill/按需读取作为一等公民——而这是更省上下文、更现代的做法。

## 五、综合建议（区分"快速修复"与"做对"）

成熟解法收敛清晰：**面向 LLM 就该输出 Markdown + 按需读取**。

### 短期（先解决最初的 bug，让本地虾"能看到"）
- 修复插件三处缺陷：`content_type→mime_type`、DM 分支读 `attachments`、纯附件消息不再被丢弃。
- 后端异步调 brain，把解析结果（哪怕纯文本）截断注入消息。

### 中期（做对，建议）
1. **brain 的 PDF 解析从 pypdf 换成 PyMuPDF4LLM**：自托管、免费、快数倍、直接出 Markdown。性价比最高，改动集中在 brain 一个文件。
2. **解析结果存一份**（仿知识库 `text_content`，存 markdown）；消息给虾**摘要 + 一个"读全文"的 skill/接口**，而非全文硬塞。后端预解析为弱模型兜底（至少有摘要）。
3. 扫描件 OCR 作为后续可选项（Docling 或云 OCR）。

---

## 六、待决策项（留给设计阶段）

1. 解析落地层级：后端预解析 / 插件解析 / skill 按需调（或组合）。
2. 解析库是否升级：pypdf → PyMuPDF4LLM（输出 markdown）。
3. 交付给虾的形式：截断注入 / 摘要+按需读取 / 全文。
4. 解析结果存储：是否落库（仿 `text_content`）、是否生成 markdown 文件、是否与知识库共用。
5. 是否需要扫描件 OCR。
6. **实测 brain 真实解析耗时**（需可用的 BRAIN_URL）——用真实数据决定"够用 vs 升级"。
